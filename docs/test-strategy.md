# Тестова стратегія — CarRental System (Лабораторна №36)

## 1. Критичні сценарії системи
Для нашої системи оренди автомобілів критичними є такі ланцюжки:
* **Валідація та цілісність домену:** Створення автомобілів з коректною вартістю та реєстрація клієнтів із валідною поштою.
* **Розрахунок замовлень:** Коректний прорахунок тривалості та підсумкової вартості оренди на основі базових тарифів доменних сутностей.
* **Persistence-цикл:** Збереження агрегатів у JSON-файли через шар інфраструктури та повне відновлення стану без втрати даних (круглий стіл даних).

## 2. Зони ризику та компоненти, що важко тестуються
* **Файлова система (I/O):** Пряма робота з накопичувачем може викликати блокування файлів, відсутність прав доступу або раптову зміну шляхів під час паралельного виконання тестів.
* **Негативні сценарії I/O:** Сценарії з пошкодженим JSON-форматом, битими байтами або порожніми файлами.
* **Вирішення (Seams for testing):** Для тестування інфраструктури застосовано патерн **Testing Seams** (тестові шви) — створення локальних контрольованих репозиторіїв та робота виключно через ізольовані тимчасові файли (`Path.GetTempFileName()`).

## 3. Використання Mocks vs Реальній Інтеграції
* **Юніт-тести:** Повністю ізольовані від зовнішнього середовища. Перевіряють бізнес-правила класів `Car`, `Customer`, `RentalOrder` без залучення дисків.
* **Інтеграційні тести:** Використовують реальні (або контрольовані тестові) реалізації `RentalRepository` та `JsonDataStore`, щоб перевірити фізичний мапінг об'єктів у текстові файли сховища. Mocks тут не використовуються для забезпечення максимальної достовірності збереження даних.
